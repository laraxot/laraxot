# Story — 6.1 Email Inbox (Notify)

**Epic:** 6 — Canali Comunicazione & AI
**Status:** backlog
**Owner:** Modules\Notify

## Intent

As a user, I want to receive inbound emails linked to CRM entities (customer, contact, site, user), so that communication history is automatically tracked within the work order context.

## Acceptance Criteria

| # | Criterion |
|---|-----------|
| AC-1 | EmailContactIdentity model + migration in Notify module with columns `email` (unique), `customer_id` (FK nullable), `customer_site_id` (FK nullable), `contact_id` (FK nullable), `user_id` (FK nullable), `meta` (json). Timestamps. |
| AC-2 | EmailConversation model + migration with columns `email` (indexed), `display_name`, `identity_id` (FK email_contact_identities nullable), `customer_id`/`customer_site_id`/`contact_id`/`user_id` (all FK nullable), `status` (open/closed/archived), `last_message_at`, `meta` (json). Timestamps. Unique on `email`. |
| AC-3 | EmailMessage model + migration with columns `conversation_id` (FK), `work_order_id`/`intervention_id`/`ai_action_proposal_id` (all FK nullable), `external_message_id` (nullable unique), `direction` (inbound/outbound), `from_email`/`from_name`, `to_email`, `subject`, `body` (longText), `status` (received/read/replied/forwarded), `processing_status` (pending/processed/failed), `payload` (json raw email), `ai_result` (json), `error`, `received_at`/`sent_at`/`processed_at`. Timestamps. Indexes on `[conversation_id, created_at]`, `direction`, `processing_status`. |
| AC-4 | Identity resolution: when an EmailMessage is created, auto-resolve sender email against EmailContactIdentity table. If match found, set conversation's customer/site/contact/user from identity. If no match, create dangling conversation with email only. |
| AC-5 | Filament Resources: EmailConversationResource (with EmailMessage RelationManager), EmailMessageResource (read-only for operator). Conversation list shows last_message_at, customer name, badge count of unread messages. Messages within a conversation shown in chronological thread. |
| AC-6 | EmailMessage processing_status badge: pending→warning, processed→success, failed→danger. Direction badge: inbound→info, outbound→primary. |
| AC-7 | Policy: EmailConversationPolicy, EmailMessagePolicy extending UserBasePolicy. Operator: view+create messages, view assigned conversations. Admin: full CRUD. |

## Dev Notes

- SRC Email module (gestionale_commesse) has 3 models: EmailContactIdentity, EmailConversation, EmailMessage — all in `Infrastructure\Models\`. Target places them in `Modules\Notify\Models\`. [Source: SRC `Modules/Email/Infrastructure/Models/*`, architecture.md#wave-6]
- SRC migration creates 3 tables with FKs to customers, customer_sites, contacts, users, work_orders, interventions, and ai_action_proposals. All FKs nullable except conversation_id on messages. [Source: SRC `Modules/Email/Database/Migrations/2026_05_14_000001_create_email_tables.php`]
- The target module is Notify (existing module in base_workorder_fila5). Notify already has a `Contact` model and a polymorphic `contact` system — the new Email models coexist with existing Notification/Template models. [Source: `laravel/Modules/Notify/app/Models/` listing]
- Identity resolution logic: EmailContactIdentity stores known email→CRM mappings. When a message arrives from a new email, an identity can be created manually or via AI matching (Epic 6.4). The `ResolveEmailIdentityAction` is the pure lookup — AI matching comes later. [Source: SRC model relationships]
- Notify's existing `Contact` model is different from EmailContactIdentity. Contact stores generic notification contact info (phone, email, SMS status). EmailContactIdentity is specifically for email address→CRM entity resolution. See existing migration `2026_06_11_180000_create_notify_contacts_table.php` for the Contact schema. [Source: `laravel/Modules/Notify/database/migrations/2026_06_11_180000_create_notify_contacts_table.php`]
- EmailMessage `ai_action_proposal_id` FK will be wired in Epic 6.4 story. Store-only here. [Source: architecture.md#wave-6]
- External email ingestion (IMAP/POP3/webhook) is NOT in scope for this story — only the data model and manual creation via Filament. Inbound ingestion is follow-up work. [Source: prd.md#FR-06, scope is "models"]
- SRC models use final keyword and `$guarded = []` — target uses `$fillable`. [Source: `laravel/AGENTS.md`]

## Testing Strategy

- Use Pest `it()` functions.
- **Model tests:** test factory creates, all relations, casts (payload, ai_result, meta → array).
- **Identity resolution:** test ResolveEmailIdentityAction with matching and non-matching emails; test automatic resolution on message create.
- **Conversation unique constraint:** test duplicate email conversation creation fails.
- **Resource tests:** page rendering (if patterns exist), conversation unread count.
- **Policy:** operator vs admin access scoping.
- No `RefreshDatabase`.
