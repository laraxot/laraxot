# Story — 6.2 WhatsApp Inbox (Notify)

**Epic:** 6 — Canali Comunicazione & AI
**Status:** backlog
**Owner:** Modules\Notify

## Intent

As a user, I want to receive inbound WhatsApp messages linked to CRM entities, so that communication via WhatsApp Business is tracked alongside emails within the work order context.

## Acceptance Criteria

| # | Criterion |
|---|-----------|
| AC-1 | WhatsAppContactIdentity model + migration with columns `phone_e164` (unique E.164 format), `wa_id` (nullable WhatsApp API ID, indexed), `customer_id`/`customer_site_id`/`contact_id`/`user_id` (all FK nullable), `meta` (json). Timestamps. |
| AC-2 | WhatsAppConversation model + migration with columns `phone_e164` (indexed), `wa_id` (nullable indexed), `display_name`, `identity_id` (FK whatsapp_contact_identities nullable), `customer_id`/`customer_site_id`/`contact_id`/`user_id` (all FK nullable), `status` (open/closed/archived), `last_message_at`, `meta` (json). Timestamps. Unique on `phone_e164`. |
| AC-3 | WhatsAppMessage model + migration with columns `conversation_id` (FK), `work_order_id`/`intervention_id`/`ai_action_proposal_id` (all FK nullable), `meta_message_id` (nullable unique), `direction` (inbound/outbound), `from_number`/`to_number`, `message_type` (text/image/document/audio), `body` (longText), `status` (received/read/replied), `processing_status` (pending/processed/failed), `payload` (json raw API payload), `ai_result` (json), `error`, `received_at`/`sent_at`/`processed_at`. Timestamps. Indexes on `[conversation_id, created_at]`, `direction`, `processing_status`. |
| AC-4 | Identity resolution (mirrors email): auto-resolve sender phone against WhatsAppContactIdentity on message create. Set conversation CRM FKs from matched identity. |
| AC-5 | Filament Resources: WhatsAppConversationResource (with WhatsAppMessage RelationManager), WhatsAppMessageResource (read-only for operator). Conversation list shows last_message_at, customer name, unread badge. Message thread in chronological order with direction badges. |
| AC-6 | WhatsAppMessage processing_status badge: pending→warning, processed→success, failed→danger. Direction badge: inbound→success (green indicates incoming), outbound→primary. message_type displayed as icon or label. |
| AC-7 | Policy: WhatsAppConversationPolicy, WhatsAppMessagePolicy extending UserBasePolicy. Operator: view+create messages, view assigned conversations. Admin: full CRUD. |

## Dev Notes

- SRC WhatsApp module structure mirrors Email module exactly: 3 models, 1 migration, same FK schema swapped for phone/wa_id. [Source: SRC `Modules/WhatsApp/Database/Migrations/2026_05_14_000001_create_whatsapp_tables.php`]
- The second SRC migration `2026_07_10_120000_add_proposal_tracking_to_whatsapp_conversations.php` adds AI proposal tracking. This can be merged into base migration if desired, or deferred — the ai_action_proposal_id FK on WhatsAppMessage already covers proposal linking. [Source: SRC migration listing]
- `phone_e164` is the canonical phone number in E.164 format (+393XXXXXXXXX). `wa_id` is the WhatsApp Business API user ID (usually the same as phone without + prefix). [Source: SRC migration field definitions]
- WhatsAppMessage `message_type` values: text, image, document, audio — stored as strings. No enum. [Source: SRC migration]
- This story intentionally mirrors story 6.1 structure. Both inbox channels share the same identity resolution pattern and FK schema. Consider extracting a shared `InboxConversation` trait or base class if duplication is high — but not required for this story (YAGNI). [Source: architecture.md#wave-6]
- No external WhatsApp Business API integration in scope — only data models. [Source: prd.md#FR-06 scope]
- The existing Notify module's `Contact` model already handles SMS channels (sms_sent_at, sms_count, sms_status_code). WhatsApp is a separate channel alongside SMS, not a replacement. [Source: `laravel/Modules/Notify/database/migrations/2026_06_11_180000_create_notify_contacts_table.php`]

## Testing Strategy

- Use Pest `it()` functions.
- **Model tests:** test factory creates, all relations, casts.
- **Identity resolution:** test ResolveWhatsAppIdentityAction with matching/non-matching phones.
- **Phone unique constraint:** test duplicate phone on WhatsAppContactIdentity and WhatsAppConversation.
- **Resource tests:** page rendering (if patterns exist), conversation thread with direction badges.
- **Policy:** operator vs admin access.
- No `RefreshDatabase`.
