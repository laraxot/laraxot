# Story — 6.4 AI Action Proposal & Tool Log

**Epic:** 6 — Canali Comunicazione & AI
**Status:** backlog
**Owner:** Modules\AI

## Intent

As an AI system, I want to propose actions to the user (start/stop time punch, upsert daily note, change work order status, etc.) and log tool calls, so that the user can confirm or reject AI-suggested operations with full audit trail.

## Acceptance Criteria

| # | Criterion |
|---|-----------|
| AC-1 | AiActionProposal model + migration with columns `public_id` (uuid unique), `ai_thread_id` (FK), `proposed_by_user_id` (FK), `type` (string — action type code like start_time_punch, stop_time_punch, upsert_daily_note, change_work_order_status, finalize_intervention_report), `payload` (json — action arguments), `preview` (longText — human-readable description), `status` (string: pending/cancelled/confirmed/executed/failed), `confirmed_by_user_id` (FK nullable), `confirmed_at` (datetime nullable), `executed_at` (datetime nullable), `result` (json nullable), `error` (longText nullable). Timestamps. |
| AC-2 | AiToolLog model + migration with columns `ai_thread_id` (FK), `ai_action_proposal_id` (FK nullable), `user_id` (FK nullable), `tool_name` (string), `arguments` (json nullable), `response` (json nullable), `status` (ok/error), `error` (longText nullable). Timestamps. |
| AC-3 | AiActionProposal has `thread()` BelongsTo, `proposedBy()` BelongsTo, `confirmedBy()` BelongsTo relations. AiToolLog has `thread()` BelongsTo, `proposal()` BelongsTo, `user()` BelongsTo. |
| AC-4 | Proposal lifecycle: pending → confirmed → executed, or pending → cancelled, or pending → failed (to handle execution errors). Status badge: pending→warning, confirmed→primary, executed→success, cancelled→danger, failed→secondary. |

| AC-7 | Filament AiActionProposalResource (admin only — operator via inline widget). AiToolLogResource (read-only, admin only). ActionProposal inline widget on WorkOrder/Intervention view pages showing pending proposals. |
| AC-8 | Policy: AiActionProposalPolicy, AiToolLogPolicy extending UserBasePolicy. Admin: full CRUD on both. Operator: view proposals on own records, confirm/cancel own proposals. |

## Dev Notes

- SRC AiAssistant migration creates ai_action_proposals and ai_tool_logs in the same file as ai_threads + ai_messages. If story 6.3's migration already ran, this story's migration only adds the two proposal/tool tables. If combined, the migration can be a single file — coordinate with story 6.3. [Source: SRC `Modules/AiAssistant/Database/Migrations/2026_02_25_000001_create_aiassistant_tables.php`]
- Action proposal types mirror the SRC intervention/workorder actions: start_time_punch, stop_time_punch, upsert_daily_note, change_work_order_status, finalize_intervention_report. The handler map is a simple array: new handlers are registered by adding entries. [Source: SRC migration enum comment]
- AiToolLog records every tool invocation for audit. It links to the thread for context and optionally to the proposal that triggered it. Direct tool calls (not via proposal) have ai_action_proposal_id = null. [Source: SRC model relationships]
- Proposal status machine: pending (default, shown to user for confirmation) → confirmed (user clicked confirm) → executed (system executed, success) / failed (execution error). Cancelled can happen from pending or confirmed (prior to execution). [Source: SRC migration]
- The handler map is stored in a config file `config/ai-action-handlers.php` returning `['start_time_punch' => StartTimePunchHandler::class]`. Handlers are invokable classes implementing `__invoke(array $payload): array`. For this story, register stub handlers that log the action and return success. Real handlers come in Epic 1 stories when intervention/workorder modules are ready. [Source: architecture.md#cross-cutting: actions]
- The ActionProposal inline widget on WorkOrder/Intervention pages requires those modules to exist. If WorkOrder/Intervention (Epic 1) is not ready, this widget is deferred. `ponytail: add widget when Epic 1 modules exist.` [Source: prd.md#FR-06 scope]
- The AI module currently has no Filament Resources or pages — this story creates the first ones. [Source: `laravel/Modules/AI/app/Filament/` listing — only Actions/ and Pages/ dirs, no Resources yet]

## Testing Strategy

- Use Pest `it()` functions.
- **Model tests:** test factory creates, all relations, casts, uuid generation.
- **Proposal lifecycle:** test status transitions (pending→confirmed→executed, pending→cancelled, pending→failed), test invalid transitions are rejected.
- **ConfirmActionProposalAction:** test sets confirmed_by, confirmed_at, status=confirmed. Test error on non-pending.
- **ExecuteActionProposalAction:** test successful execution sets executed_at and status=executed. Test error sets status=failed and populates error field.
- **Handler map:** test registered handler resolve, test unknown type returns error.
- **AiToolLog:** test creates with correct thread/ proposal FK, status badge.
- **Policy:** admin vs operator access.
- No `RefreshDatabase`.
