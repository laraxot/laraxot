# Story — 6.3 AI Thread & Message

**Epic:** 6 — Canali Comunicazione & AI
**Status:** backlog
**Owner:** Modules\AI

## Intent

As an AI system, I want to persist conversation threads and messages, so that the assistant has context across turns within the Filament panels.

## Acceptance Criteria

| # | Criterion |
|---|-----------|
| AC-1 | AiThread model + migration in AI module with columns `public_id` (uuid unique), `created_by_user_id` (FK users), `panel_id` (string, default 'operator'), `last_message_at` (nullable datetime), `meta` (json nullable). Timestamps. |
| AC-2 | AiMessage model + migration with columns `ai_thread_id` (FK), `user_id` (FK nullable), `role` (user/assistant/tool/system), `content` (longText nullable), `payload` (json nullable — tool args/results/structured output). Timestamps. |
| AC-3 | AiThread has `createdBy()` BelongsTo User, `messages()` HasMany, `proposals()` HasMany, `toolLogs()` HasMany relations. AiMessage has `thread()` BelongsTo, `user()` BelongsTo relations. |
| AC-4 | Filament AiThreadResource with List (sortable by last_message_at desc), View page with threaded AiMessage display. Create/Edit handled via AI chat interface (not standard CRUD). Messages displayed in chronological order, role badges: user→primary, assistant→success, tool→warning, system→gray. |
| AC-5 | Panel scoping: AiThread lists filtered by `panel_id` (operator vs admin panel). Each panel only sees its own threads. |
| AC-6 | AiMessage `role` cast to string; `payload` cast to array. AiThread `public_id` auto-generated UUID on create. `last_message_at` auto-updated on each new message via thread's `touch()` or booted event. |
| AC-7 | Policy: AiThreadPolicy extending UserBasePolicy. Operator: view own threads, create messages. Admin: view all threads. |

## Dev Notes

- SRC AiAssistant module has 4 models: AiThread, AiMessage, AiActionProposal, AiToolLog. This story covers only AiThread + AiMessage. AiActionProposal + AiToolLog are in story 6.4. [Source: SRC `Modules/AiAssistant/Infrastructure/Models/`, architecture.md#wave-6]
- SRC migration creates all 4 tables in one file. For the target, split: this story creates ai_threads and ai_messages; story 6.4 adds ai_action_proposals and ai_tool_logs via a subsequent migration or extension of the same migration. [Source: SRC `Modules/AiAssistant/Database/Migrations/2026_02_25_000001_create_aiassistant_tables.php`]
- The AI module in base_workorder_fila5 currently has no models (Models directory has only .gitkeep). This story bootstraps the module's model layer. [Source: `laravel/Modules/AI/app/Models/`]
- Existing Actions in the AI module (CompletionAction, SentimentAction) are standalone Actions that do not depend on models — they will integrate with AiThread/AiMessage via the thread_id/message_id in a follow-up. [Source: `laravel/Modules/AI/app/Actions/`]
- Panel scoping via `panel_id` string column enables multi-panel AI assistant: operator panel sees only operator threads, admin panel sees admin threads. A future cross-panel thread share could use a pivot or team-based visibility. [Source: SRC migration field panel_id]
- SRC AiThread uses `$guarded = []` + `protected function casts()` — target uses `$fillable` + `$casts`. [Source: `laravel/AGENTS.md`]
- SRC model naming: SRC uses `Modules\AiAssistant\Infrastructure\Models\AiThread`. Target uses `Modules\AI\Models\AiThread`. [Source: architecture.md#module-boundary-architecture]
- The module name is `AI` (uppercase), not `AiAssistant`. Namespace: `Modules\AI\Models\`. [Source: `laravel/Modules/AI/`]

## Testing Strategy

- Use Pest `it()` functions.
- **Model tests:** test factory creates, AiThread uuid generation, AiMessage role cast, thread→messages HasMany, messages→thread BelongsTo.
- **last_message_at:** test auto-update on message creation; test it does NOT update on message edit.
- **Panel scoping:** test operator sees only operator panel threads, admin sees admin panel threads.
- **Policy:** test operator CRUD on own threads, admin sees all.
- No `RefreshDatabase`.
