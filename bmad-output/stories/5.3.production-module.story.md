# Story — 5.3 Production Module

**Epic:** 5 — Manufacturing & Verticali
**Status:** backlog
**Owner:** Modules\Production

## Intent

As a production manager, I want to create and track production orders with phased execution, so that manufacturing progress is visible and accountable.

## Acceptance Criteria

| # | Criterion |
|---|-----------|
| AC-1 | ProductionOrder model + migration with columns `code` (nullable unique), `product_id` (FK products), `quantity` (integer default 1), `status` (string: planned/in_progress/completed/cancelled), `work_order_id` (FK nullable), `notes` (text nullable), `due_at` (datetime nullable). Indexes on `product_id`, `status`, `work_order_id`. |
| AC-2 | ProductionPhase model + migration with columns `production_order_id` (FK), `name`, `sort_order` (unsigned int default 0), `status` (string: planned/in_progress/completed/blocked), `assigned_to_user_id` (FK users nullable), `started_at` (datetime nullable), `completed_at` (datetime nullable). Indexes on `production_order_id`, `status`. |
| AC-3 | ProductionOrder has `product()` BelongsTo, `workOrder()` BelongsTo, `phases()` HasMany (ordered by sort_order). ProductionPhase has `productionOrder()` BelongsTo, `assignedTo()` BelongsTo. |
| AC-4 | Filament ProductionOrderResource with List, Create, Edit, View pages. Status badge colors: planned → gray, in_progress → warning, completed → success, cancelled → danger. Phases managed as Repeater or RelationManager. |
| AC-5 | Status machine: ProductionOrder cannot transition from completed/cancelled to any other status. Phase status can only advance planned→in_progress→completed or planned→blocked→planned. Validation on save. |
| AC-6 | Operator scope: ProductionPhase filters to `assigned_to_user_id = auth()->id()`. Admin sees all. Phase status toggle actions for assigned operator. |
| AC-7 | Policy: ProductionOrderPolicy and ProductionPhasePolicy extending UserBasePolicy. |

## Dev Notes

- SRC Production module has a single migration creating both tables. No subsequent migrations. [Source: SRC `Modules/Production/Database/Migrations/2026_02_25_000030_create_production_tables.php`]
- ProductionOrder links to Product (Catalog, Epic 3) and WorkOrder (Epic 1). Both must exist. [Source: architecture.md#wave-5]
- SRC status values are English strings: planned/in_progress/completed/cancelled (order), planned/in_progress/completed/blocked (phase). Keep as-is. [Source: SRC migration]
- Phase `sort_order` enables drag-reorder in Filament (via `spatie/eloquent-sortable` or manual order). For this story, manual order entry is sufficient. [Source: SRC migration]
- ProductionOrder `code` auto-generation is TBD — could use a prefix like `PO-{year}-{sequential}`. For now nullable unique on migration level, generated via creating event if null. [Source: SRC migration]
- No SoftDeletes on either table in SRC — replicate without soft deletes unless explicitly needed. [Source: SRC migration]

## Testing Strategy

- Use Pest `it()` functions.
- **Model tests:** test factory create, relations, status casts, sort_order ordering.
- **Status machine:** test valid transitions, test invalid transitions throw or are ignored, test completed/cancelled terminal state enforcement.
- **Resource tests:** page rendering (if patterns exist), status badge colors, phase Repeater/RelationManager.
- **Operator scope:** test operator sees only assigned phases, admin sees all phases.
- **Policy:** test CRUD access for admin vs operator.
- No `RefreshDatabase`.
