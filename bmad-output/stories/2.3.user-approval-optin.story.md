# Story — 2.3 User Approval Opt-In

**Epic:** 2 — HR & User Alignment
**Status:** backlog
**Owner:** Modules\User

## Intent

As an admin, I want to approve new user registrations, so that only authorized users access the system.

## Acceptance Criteria

| # | Criterion |
|---|-----------|
| AC-1 | Migration adds `approved_at` (datetime nullable) and `approved_by_user_id` (FK users nullable) columns to `users` table. Index on `approved_at`. |
| AC-2 | `ApproveRegisteredUserAction` (Spatie QueueableAction) sets `approved_at = now()`, `approved_by_user_id` from argument. Optionally syncs a default role (e.g. `operator`) via `$user->syncRoles(...)`. |
| AC-3 | UserResource table gains an "Approve" action button visible only for records where `approved_at IS NULL`. Button triggers `ApproveRegisteredUserAction`. Color: success. Icon: heroicon-o-check. Requires confirmation. |
| AC-4 | Registration flow detects if approval is enabled (config flag `user.approval_required`). If enabled, after registration the user sees a "pending approval" screen (Folio page or Volt component) instead of being logged in. A middleware or listener blocks login for unapproved users who are not admin. |

## Tasks

| # | Task | AC |

| T-1 | Create migration `add_approval_fields_to_users_table`: `approved_at timestamp null`, `approved_by_user_id bigint unsigned null FK→users`, index on `approved_at`. | AC-1 |

## Dev Notes

- SRC Auth has `ApproveRegisteredUserAction` in `Modules/Auth/Application/Actions/ApproveRegisteredUserAction.php`. The pattern is identical: set `approved_at`, `approved_by_user_id`. Our User model already has all the Spatie Permission infrastructure (roles sync). [Source: `gestionale-auth-vs-user.md:35`]
- SRC uses `customer_id` on users table for portal access — NOT porting that. Our approach is Customer module + membership, not a column on users. [Source: `gestionale-auth-vs-user.md:38`]
- User model currently has no `approved_at` / `approved_by_user_id` columns. Model file is at `Modules/User/app/Models/User.php`. [Source: inspection of model]
- User model uses `Modules\User\Models\BaseUser` as parent (not shown here but confirmed from xdebug/ide helper). May need to add fields to `$fillable` on User.
- Existing UserResource is in `Modules\User\Filament\Resources\UserResource` — read its current form/table to understand where to add the Approve action. Must not break existing functionality.
- Approval is opt-in via config flag. Default off, backward compatible. SRC always requires approval; our system keeps it optional. [Source: `gestionale-auth-vs-user.md`: «Non equivalente prodotto / Portare come opt-in Tenant/User se serve onboarding controllato»]
- The login gate can be a `Login` event listener in `Modules/User/app/Listeners/` that checks `approved_at` before session creation, or a middleware on the Folio login Volt page. Prefer listener on `Illuminate\Auth\Events\Login` to keep it decoupled.

## Testing Strategy

- Pest `it()` for `ApproveRegisteredUserAction`: create unapproved user, execute action, assert `approved_at` is set, `approved_by_user_id` matches, role synced when provided.
- Migration test: roll up/down, assert columns exist.
- Model test: `$user->approvedBy()` returns the admin user.
- Login gate test: create unapproved user, attempt login with `config('user.approval_required') = true`, assert login blocked.
- UserResource test: approve action visible only for unapproved records.
