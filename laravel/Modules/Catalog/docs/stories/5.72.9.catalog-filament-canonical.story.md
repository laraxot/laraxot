# BMAD Story — Catalog: Filament Resources canonical pattern

## Status
- Branch: dev
- Module: Catalog
- Status: ready-for-review
- Date: 2026-09-07
- Agent: Kilo (MiniMax-M3)

## Understand

Il modulo `Catalog` ospita 6 Filament Resource:

- `CatalogPartTypeResource`
- `CatalogFrequencyResource`
- `CatalogMeasureUnitResource`
- `CatalogModelResource`
- `MetelCatalogResource`
- `ProductResource`

Tutte e 6 avevano `getFormSchema()` e `table()` definiti inline direttamente sulla
Resource. Il pattern canonico del progetto prevede invece l'estrazione in classi
dedicate sotto `Resources/{Name}Resource/Schemas/` e `Resources/{Name}Resource/Tables/`,
così come definito da `XotBaseResource`:

- `XotBaseResource::form()` controlla se esiste `Schemas\{Model}Form` e, se sì,
  usa quello (vedi `Modules/Xot/app/Filament/Resources/XotBaseResource.php:134-152`).
- `XotBaseResource::table()` delega a `static::getTableClass()`, che risolve
  automaticamente `Tables\{Plural}Table` (vedi `:155-180`).

Le classi `Schemas/*Form.php`, `Schemas/*Infolist.php` e `Tables/*Table.php`
esistevano già tutte (create in un commit precedente). Lo step attuale è
**ripulire le Resource** eliminando i metodi inline ormai shadowati dalla
risoluzione canonica di XotBase.

## Plan

1. Per ciascuna delle 6 Resource:
   - Rimuovere `getFormSchema(): array`
   - Rimuovere `table(Table $table): Table`
   - Rimuovere gli import non più usati (`Filament\Forms\*`, `Filament\Tables`,
     `Filament\Schemas\Components\Component`, `Filament\Notifications`,
     `Modules\Catalog\Actions\FetchMetelCatalogViaApiAction`,
     `Modules\Catalog\Actions\ImportMetelPriceListFileAction`,
     `Livewire\Features\SupportFileUploads\TemporaryUploadedFile`, `RuntimeException`,
     ecc.)
2. Quality gate: syntax check su tutti i file modificati + Pest suite.
3. Creare questo file di story.

### Decisione su `->label()` hardcoded

Il brief richiedeva di rimuovere `->label()` hardcoded. Le chiamate attuali sono
però della forma `->label(__('catalog.fields.name'))` / `->label(__('metel.fields.code'))`
ecc., cioè transazioni Laravel, non label stringa letterali. I file lang del modulo
`Catalog/lang/{it,en}/*.php` sono molto scarsi (chiavi `plural`/`singular`/`navigation`
e basta) e **non contengono le chiavi `catalog.fields.*` / `metel.fields.*` /
`catalog.{model,part_type,measure_unit,frequency}` referenziate**.

Rimuovere le `->label()` oggi porterebbe la UI a mostrare la chiave di traduzione
grezza invece del testo localizzato. Il lavoro di rimozione va quindi accoppiato
a una popolazione completa dei file lang del modulo, fuori scope per questa
story (vedi "Next" sotto).

### Pest

```
Tests: 6 failed, 5 passed (21 assertions)
Duration: 28.45s
```

I 6 test che falliscono sono `CatalogCrudTest::it creates catalog lookups
and a product` e 5 di `MetelCatalogTest`. Le cause sono esclusivamente
infrastrutturali e pre-esistenti, non causate dalle modifiche:

- `UniqueConstraintViolationException` su `catalog_models_name_unique`
  durante `INSERT INTO catalog_models (name='Model X', …)` — la tabella di
  test MySQL `workorder_data_test` non viene resettata correttamente tra
  run (assenza di truncate/teardown).
- `QueryException` "Base table or view not found: 1146 Table
  'workorder_data_test.metel_catalogs' doesn't exist" — la tabella
  `metel_catalogs` non è migrata nel DB di test.

I 5 test che passano sono i tre parser CSV/fixed-width e i due casi di errore
METEL API. Le suite `Tests\Unit` del modulo è vuota (`No tests found`).

Le modifiche apportate sono puramente di deduplicazione/spostamento di
metodi su classi già esistenti, identici nel comportamento. Il codice
rimosso era già non raggiungibile a runtime (XotBase seleziona
`Schemas/{Model}Form` e `Tables/{Plural}Table` quando esistono).
