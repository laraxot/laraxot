## Story

**As a** Laravel developer maintaining the Catalog module
**I want** the 6 Catalog Filament Resources to stop overriding `table()` and instead delegate to dedicated `XotBaseResourceTable` subclasses
**So that** Catalog respects the Liskov Substitution Principle already encoded in `XotBaseResource`/`XotBaseResourceTable`, and its list pages stop silently bypassing the shared table-configuration pipeline

## Acceptance Criteria

## Dev Notes

### The rule (LSP, in the user's own framing)

`XotBaseResource::table(Table $table): Table` is the one place this method is meant to be
defined for any Resource in the tree: it calls `static::getTableClass()` (which resolves
`{ResourceNamespace}\Tables\{ModelOrResourcePlural}Table` and asserts it is a subclass of
`XotBaseResourceTable`), then delegates to `$class::configure($table)`.
[Source: laravel/Modules/Xot/app/Filament/Resources/XotBaseResource.php lines 157-180]

`XotBaseResourceTable::configure()` instantiates the concrete Table class and calls its
`table()` method, which is supplied by the `HasXotTable` trait and reads the columns/filters/
actions from hook methods (`getTableColumns()`, `getTableFilters()`, `getTableActions()`,
`getTableBulkActions()`, etc.) that the concrete Table class overrides.
[Source: laravel/Modules/Xot/app/Filament/Resources/Tables/XotBaseResourceTable.php lines 19-40;
laravel/Modules/Xot/app/Filament/Traits/HasXotTable.php lines 220-274]

A Resource that declares its own `static function table(Table $table): Table` — as all 6
Catalog Resources currently do — never reaches `getTableClass()`. Per the user's brief: LSP
says a subclass must be usable wherever the base type is expected; `XotBaseResource`'s
contract for `table()` is "resolve and delegate to the paired Table class", and a Resource
that redefines `table()` to build the table inline breaks that contract silently (no error,
no warning — the override is simply never bypassed, it *is* the code path Filament calls, so
the base's dispatch logic is skipped entirely). This is corroborated by the project's own
guideline doc, which documents the exact same failure mode for the (structurally identical)
List-page variant of this bug: "*i filtri non compaiono*" — no crash, just silently wrong
behaviour. [Source: laravel/Modules/Xot/docs/filament-table-architecture.md, "Come accorgersi
che si sta sbagliando" section]

### Actions gotcha — read before writing the Table classes

`HasXotTable::getTableActions()`'s default implementation only adds `ViewAction`/`EditAction`/
`DeleteAction` if `method_exists($resource, 'canView'/'canEdit'/'canDelete')` — and when called
from a `XotBaseResourceTable` subclass (not a `ListRecords` page), `$resource` is the Table
class instance itself, which does not define those methods anywhere in this codebase.
[Source: laravel/Modules/Xot/app/Filament/Traits/HasXotTable.php lines 303-340] The default
`getTableBulkActions()` supplies only a plain `DeleteBulkAction`.
[Source: laravel/Modules/Xot/app/Filament/Traits/HasXotTable.php lines 372-381]

Concretely: if the new Table classes only implement `getTableColumns()` (as
`Modules\Blog\...\ArticlesTable` does), the row-level View/Edit buttons that the 6 Catalog
Resources currently render **will silently disappear**, and `ProductsTable`/`MetelCatalogsTable`
will lose their soft-delete/custom actions. Every one of the 6 new Table classes in this story
must explicitly override `getTableActions()` (and, for Product, `getTableBulkActions()`) to
reproduce the exact action set the removed `table()` body built. `[Inference — derived from
reading the trait's default logic; not independently executed by this agent]`
