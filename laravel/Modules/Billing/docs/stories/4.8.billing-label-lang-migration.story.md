# Story 4.8 — Billing: rimuovere ->label() hardcoded

## Understand

### Problem

Dopo la migrazione Schemas/Tables (story 4.1), le Resources Billing hanno ancora
->label(__('...')) hardcoded nei Form. Rimuoverli ora romperebbe l'UI perche le chiavi
esistenti in lang/it/suppliers.php non coincidono con le chiavi auto-derivate da
LangServiceProvider.

### Delta analisi

Chiavi in `lang/it/suppliers.php`:

```php
'fields' => [
    'number', 'supplier', 'legal_name', 'vat_number', 'email', 'phone',
    'is_active', 'received_on', 'issued_on', 'notes', 'total', 'status',
    'description', 'quantity', 'unit_price', 'line_total', 'lines_count',
    'delivery_notes_count', 'invoices_count', 'work_order',
]
```

Chiavi auto-derivate da LangServiceProvider per un campo 'number' su un field
con nome derivato dal Model (notazione corretta `modulo::chiave`, non
`modulo.chiave` — vedi story 4.12 per l'algoritmo esatto,
`Modules\Xot\Actions\GetTransKeyAction`):

```
billing::delivery_note.fields.number.label
billing::invoice.fields.number.label
billing::supplier.fields.number.label
billing::supplier_invoice.fields.number.label
```

Dettaglio tecnico (classi sorgente, verifica contro un esempio reale funzionante
`Modules/Gdpr/lang/it/treatment.php`): story
[4.12](./4.12.billing-label-translation-key-detail.story.md) — companion di questa,
non un piano alternativo.

Le chiavi attuali in lang non usano la convenzione dot-notation
(modulo.resource.fields.campo.label).

## Plan

1. Elencare tutti i ->label(__('billing::...')) nelle 4 Resources (grep)
2. Per ogni campo con ->label(), verificare se la chiave corrispondente esiste in lang/
3. Se la chiave esiste: rimuovere ->label() (funziona gia)
4. Se la chiave NON esiste: crearla in lang/it/suppliers.php o billing.php, poi rimuovere ->label()
5. Quality gate

- [ ] `php artisan tinker: "Lang::get('billing::...')" risponde in italiano — non ancora verificato, atteso NO (vedi sotto)
- [ ] `php artisan serve` mostra label corrette — non ancora verificato

## CONFERMATO IN PRODUZIONE (non più solo un rischio ipotetico)

Verificato per traccia diretta del codice, non per analogia: `GetTransKeyAction::execute()`
(`Modules/Xot/app/Actions/GetTransKeyAction.php`) per la classe chiamante
`Modules\Billing\Filament\Resources\DeliveryNoteResource\Tables\DeliveryNotesTable`
produce `$module_low.'::'.$class_snake` = **`billing::delivery_notes`** (non
`billing.delivery_note.fields...` con i punti come scritto sopra — la chiave usa `::` per il
namespace del file lang, `.` solo per i segmenti dentro). Nessuna traduzione esiste li'.

`Modules/Billing/lang/it/delivery_note.php` **esiste già** (committato, pushato su `dev`),
generato automaticamente da `SaveTransAction` la prima volta che il componente è stato
renderizzato/toccato: contiene solo placeholder identici al nome campo, non le traduzioni
curate:

```php
'fields' => [
    'number' => ['label' => 'number', ...],           // atteso: 'Numero'
    'received_on' => ['label' => 'received_on', ...], // atteso: 'Data ricevimento'
    'notes' => ['label' => 'notes', ...],              // atteso: 'Note'
],
```

I `->label(__('billing::suppliers.fields.*'))` sono **già stati rimossi** da
`Schemas/DeliveryNoteForm.php` e `Tables/DeliveryNotesTable.php` (0 occorrenze, verificato
sopra). Il form/la tabella DDT mostrano quindi **oggi, su `dev`**, "number"/"received_on"/
"notes" al posto di "Numero"/"Data ricevimento"/"Note" — non è più un rischio da "Plan", è un
difetto UI reale già live. Priority alzata a P0 di conseguenza.

**Fix minimo**: i file `lang/it/{delivery_note,invoice,supplier_invoice,supplier}.php` esistono
già con la struttura giusta (auto-generata) — basta sostituire i valori placeholder con quelli
già curati in `suppliers.php`/`supplier.php`, non serve ricreare la struttura.
