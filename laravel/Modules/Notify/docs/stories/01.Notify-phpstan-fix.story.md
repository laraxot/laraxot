## Solution

Poiche' non c'erano errori PHPStan da correggere, il lavoro si e' spostato
sulle richieste esplicite collaterali del task (mixed reduction, UserContract)
con verifica PHPStan ad ogni modifica (nessuna regressione ammessa):

1. **`app/Notifications/TicketAssignedNotification.php`** — unico file in
   `app/` che referenziava il model concreto `Modules\User\Models\User`
   invece del contratto:
   - `public User $assignedBy` → `public UserContract $assignedBy`
     (`Modules\Xot\Contracts\UserContract`), stesso pattern gia' in uso in
     `app/Datas/RecordNotificationData.php` e
     `app/Models/Policies/MailTemplatePolicy.php`.
   - `public mixed $ticket` → `public object $ticket` (nessun model `Ticket`
     nel modulo; i chiamanti passano un `Model` Eloquent o un oggetto
     generico — vedi test). Allineato al pattern gia' presente nella classe
     gemella `TicketStatusChangedNotification` che usa `object $notifiable`.
   - `via(mixed $notifiable)`, `toMail(mixed $notifiable)`,
     `toArray(mixed $notifiable)` → `object $notifiable` (la classe base
     `Illuminate\Notifications\Notification` non dichiara questi metodi, zero
     vincoli di contravarianza; stesso pattern della classe gemella).
   - **Bug latente scoperto dal narrowing**: `toArray()` dichiarava
     `@return array{assigned_by: string}` ma `UserContract::$id` e'
     `string|null` (vedi docblock del contratto) — con `User` concreto
     PHPStan non aveva un tipo preciso per `->id` e non lo aveva mai
     rilevato. Corretto a `array{assigned_by: string|null}`: riflette la
     realta' del contratto invece di promettere una garanzia non vera.
2. Verificato che non esistono altri usi di `Modules\User\Models\User` /
   `Modules\...\Models\Profile` concreti in `app/` (grep mirato, 0 risultati
   residui).
3. Non toccati gli altri 103 file con `mixed` in `app/`: la maggior parte e'
   gia' stata analizzata e motivata in `4.28.mixed-type-reduction.story.md`
   (contratti multi-provider SMS/WhatsApp/Telegram con shape di ritorno
   eterogenee, bag di config da env, DTO Spatie-Data con `definition()`
   idiomatico) — riaprire quell'analisi file-per-file senza un nuovo errore
   PHPStan a giustificarla sarebbe scope creep rispetto al mandato
   "PHPStan L10 fix".

## Dev Notes

- Working tree fortemente sporca all'avvio: 189 file con modifiche non
  committate, di cui **188 sono file di documentazione/`.planning`/`.github`
  estranei a Notify** (contaminazione da merge storici `--allow-unrelated-
  histories` di progetti host come FixCity, vedi memoria second-brain
  `feedback_modules_agnostic_no_fixcity`) e **1 solo file di codice**
  (`app/Models/NotificationType.php`, rimozione di un import inutilizzato di
  `NotificationTypeFactory` dopo la rimozione del trait `HasFactory` nel
  commit `8f7e4e9f`). Per rispettare "minimal impact" questa story **non**
  include i 188 file estranei nel commit: `git add` mirato solo ai file
  toccati.
- **Blocker di infrastruttura git risolto localmente**: `refs/remotes/
  laraxot/dev` (anche dopo `git fetch` pulito e un clone fresco di verifica
  in `/tmp`) ha una history con un parent mancante
  (`2c641c73c5ab1282c044f3436ac2573cb73d28e0`, referenziato da due commit
  duplicati "chore(gitattributes): sync dal prototipo canonico" —
  `3096f6ae` e `84e1d920`). Questo rendeva impossibile qualsiasi comando che
  attraversi la history (`git status` non-porcelain, `git merge-base`, `git
  push` incluso `--dry-run`) con `fatal: Failed to traverse parents`. **Non
  e' una corruzione locale**: riprodotta identica su un `git clone` pulito da
  GitHub, quindi e' nello storico remoto stesso (probabile commit costruito
  a mano con un parent hash stantio, poi diventato irraggiungibile). Non
  essendo permesso alcun rewrite/force-push della history remota, ho
  applicato un workaround locale non distruttivo e reversibile: `git
  replace --graft` sui due commit rotti (li fa apparire come radice per la
  sola traversal locale, senza toccare gli hash reali ne' modificare alcun
  contenuto). I refs `refs/replace/*` sono locali, **non vengono pushati**.
  Dopo il workaround: `git status` e `git push --dry-run laraxot dev`
  funzionano (`a876ae18..8f7e4e9f dev -> dev`, fast-forward pulito, dev
  locale gia' 20 commit avanti). Segnalato anche in `docs/chat/` per non far
  perdere tempo ad altri agenti sullo stesso modulo.
