# Story 3.4 — Signage: re-fix constantTypeCoverage regression

Status: **done** — 2026-09-07

## Contesto

Continuazione delle story root `2.8.phpstan-constant-type-coverage` e
`5.1.phpstan-constant-type-coverage-remaining` (claim
`docs/chat/2026-09-07-claim-typecoverage-final-push-swarm.md`, batch Quotation
12 costanti / Signage 7 costanti).

Le 7 costanti erano gia' state tipizzate oggi dal commit `28d7bd4`
("fix(signage): type constants for typeCoverage.constantTypeCoverage + fix
wrong @var shape regression", 15:16:09). Una verifica full-tree successiva le
ha ritrovate **non tipizzate**: il working tree del modulo aveva gia' 12 file
modificati + 10 cartelle/file nuovi non committati dallo swarm Epic4
"filament-canonical-structure" (story `4.14.9.signage-canonical`, gia'
osservato e documentato in standdown alle 19:12 nello stesso giorno) che
rigenera i 5 `Sign*Resource` e le loro pagine da una base precedente al fix,
perdendo silenziosamente l'annotazione di tipo nativo sulla costante.

## Perche' scoping full-tree e non per-modulo

`./vendor/bin/phpstan analyse Modules/Signage` da solo **non rileva mai**
`typeCoverage.constantTypeCoverage`: la regola
(`TomasVotruba\TypeCoverage\Rules\ConstantTypeCoverageRule`) confronta i path
analizzati da CLI con `parameters.paths` di `phpstan.neon` via
`ScopeConfigurationResolver::areFullPathsAnalysed()` e si disattiva
silenziosamente se non coincidono esattamente. Serve sempre
`analyse Modules` (l'intero albero) per vedere questi errori.
