# Story 2.9 — GatedXotBaseResource → XotBaseResource diretto (repo-wide)

## Understand

### Problem

L'utente ha corretto esplicitamente (2026-09-07, durante l'audit Filament di
Billing): "non devi utilizzare GatedXotBaseResource ma direttamente
XotBaseResource". Regola generalizzata: ogni Filament Resource estende
`XotBaseResource` direttamente, mai una sottoclasse con nome inventato
(`GatedXotBaseResource` o varianti simili) anche quando quella sottoclasse è
solo un thin wrapper (`abstract class GatedXotBaseResource extends
XotBaseResource { use GatesResourceNavigation; }`). L'autorizzazione è un
concern, non un'identità: si compone via trait/policy/scope direttamente sul
Resource concreto, non via classe intermedia "che è la versione gated".

### Root cause del caso Billing (verificato live)

`Billing\InvoiceResource` estendeva `GatedXotBaseResource` ma aveva **già**
`canView()`/`canEdit()`/`shouldRegisterNavigation()` custom via
`AccountFeatures::currentPanelAllowsFeature()`. Il layer `GatesResourceNavigation`
(basato su `NavigationGate`) non veniva mai consultato: era un secondo layer di
gating morto, mai attivato. Non è detto che questo sia vero ovunque: altri
moduli potrebbero usare `GatedXotBaseResource` SENZA logica di gating propria,
nel qual caso il trait `GatesResourceNavigation` è l'unica fonte reale di quel
comportamento e va comunque preservato (composto direttamente, non tramite la
sottoclasse con nome).

## Plan

Per ciascuno dei 13 moduli rimanenti, per ciascun Resource:

1. Leggi il Resource: ha già `canView()`/`canEdit()`/`canCreate()`/
   `shouldRegisterNavigation()` custom con logica equivalente o sovrapposta a
   `GatesResourceNavigation`?
   - **Sì, logica duplicata** → cambia `extends GatedXotBaseResource` in
     `extends XotBaseResource`, verifica che nessun comportamento sparisca
     (il trait non veniva comunque consultato).
   - **No, il trait è l'unica fonte del gating** → `extends XotBaseResource`
     + `use GatesResourceNavigation;` diretto sul Resource concreto (stesso
     comportamento, niente classe intermedia con nome).
2. `php -l` + `phpstan analyse Modules/<Mod>` dopo ogni file.
3. Verifica comportamento: se esistono test Pest sul Resource (autorizzazione,
   visibilità navigazione), rilanciali. Se non esistono, valuta se aggiungerne
   uno minimo (verifica che l'istanza sia `instanceof XotBaseResource` e non
   `GatedXotBaseResource`).
4. Quality gate completo per modulo (phpstan + phpmd + phpinsights + pest).
5. Non toccare `GatedXotBaseResource.php` stesso finché tutti i 34 consumer
   non sono migrati (evita di rompere import da qualche parte non ancora
   auditata) — solo a migrazione completata, valutare se deprecarla/rimuoverla.
