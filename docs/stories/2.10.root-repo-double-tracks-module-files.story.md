# Story 2.10 — Root repo traccia doppio i file dei moduli

## Understand

### Problem

Ogni modulo in `laravel/Modules/<X>/` ha una directory `.git` propria e
indipendente (confermato: `find laravel/Modules/<X> -maxdepth 1 -name .git`
positivo per tutti i moduli controllati — MetalWork, PublicProcurement,
Signage, Timber, Vehicle, Wts, Job, Blog, Rating, Xot, Cms, UI, AI, Media).

**Ma** `git status` lanciato dalla ROOT del repo (`base_workorder_fila5`)
mostra modifiche file-per-file DENTRO quelle stesse directory (es. `M
laravel/Modules/MetalWork/app/Actions/EstimateFromBillOfMaterialsAction.php`),
e `git ls-files laravel/Modules/MetalWork/app/Actions/
EstimateFromBillOfMaterialsAction.php` conferma che il file È tracciato anche
dal repo root, non solo dal `.git` del modulo.

In git normale, una sottodirectory con un proprio `.git` è un "embedded
repository": il repo padre la tratta come gitlink opaco (o la ignora se non
registrata come submodule/gitlink), MAI come file-per-file. Vedere diff
file-per-file dalla root significa che questi path sono stati aggiunti
all'indice del repo root come blob ordinari **prima** che i moduli avessero
il proprio `.git`, o tramite un `git add -f`/tooling che ha bypassato il
rilevamento di embedded-repo — e non sono mai stati rimossi dall'indice root
dopo.

### Perché è un problema reale

1. **Rischio di commit nel posto sbagliato**: chi lancia `git add -A` dalla
   root (compreso questo stesso agente, in altre sessioni) rischia di
   committare contenuto di modulo nel repo shell monorepo invece che nel
   repo indipendente del modulo — silenzioso, nessun errore.
2. **Falsi "delete"**: quando un agente sposta file dentro un modulo (es. lo
   swarm di root-md-hygiene di questa sessione, che ha spostato 138 file
   Xot da root a `docs/archived/` DENTRO il git di Xot), il repo ROOT li
   vede come `D` (cancellati) perché la sua copia stale del path non è mai
   stata aggiornata — nessuna cancellazione è avvenuta davvero, ma un
   controllo superficiale sullo stato root potrebbe far pensare il
   contrario.
3. **Ambiguità di ownership**: due indici git (root + modulo) per lo stesso
   file, potenzialmente divergenti, senza un meccanismo che li tenga
   sincronizzati.

### Scoperta (2026-09-07, questa sessione)

`git status --short` dalla root, durante il lavoro sulla campagna
typeCoverage, ha mostrato contemporaneamente:
- ~60 file `M` dentro moduli attivamente lavorati da agenti diversi
  (Billing, Blog, Catalog, Compliance, Customer, HR, Intervention,
  MetalWork, Platform, Production, PublicProcurement, Quotation, Rating,
  Signage, Timber, Vehicle, WorkOrder, Wts)
- 150+ file `D` sotto `laravel/Modules/Xot/` — in realtà solo spostati
  (non cancellati) dentro il `.git` indipendente di Xot dallo swarm
  root-md-hygiene di questa stessa sessione

### Non verificato

- **Portata esatta**: non è chiaro se OGNI file di OGNI modulo è
  double-tracked, o solo un sottoinsieme storico (es. i file che esistevano
  prima che il modulo ottenesse il proprio `.git`). Richiede un controllo
  sistematico: `git ls-files laravel/Modules/<X>/ | wc -l` vs il conteggio
  reale di file nel modulo, per ciascun modulo.
- **Origine storica**: non è chiaro QUANDO/COME questo doppio tracking sia
  iniziato — richiede `git log --follow` su alcuni path campione, o intervista
  all'owner sulla storia del repo (monorepo→moduli indipendenti? moduli
  indipendenti→imported come blob per errore?).

## Segnalato all'utente, nessuna decisione presa

L'utente, interrogato su come gestirlo (segnalare-e-basta vs indagare portata
prima), ha risposto pivotando su un argomento diverso (regola frontmatter
issue/discussion) — non ha dato una disposizione esplicita su QUESTO problema.
Questa story esiste per non perdere la scoperta, non per un piano d'azione:
**nessuna azione è stata presa sui file double-tracked**, nessun `git rm
--cached` è stato eseguito.

## Plan (da validare con l'owner prima di eseguire QUALSIASI passo)

1. Misurare la portata reale (script sopra) su tutti i ~40+ moduli.
2. Chiedere all'owner: il double-tracking è intenzionale (motivo?) o un
   residuo storico da ripulire?
3. Se da ripulire: `git rm -r --cached laravel/Modules/<X>` per ogni modulo
   double-tracked (rimuove dall'indice ROOT senza toccare i file su disco né
   il `.git` del modulo), poi verificare che `.gitignore` della root escluda
   `laravel/Modules/*/` esplicitamente per prevenire la ricomparsa.
4. Se intenzionale: documentare il PERCHÉ in `docs/wiki/` per evitare che
   futuri agenti (incluso questo, in sessioni future) lo segnalino di nuovo
   come bug.

## Acceptance Criteria (Definition of Done)

- [ ] Portata esatta misurata e documentata (quali moduli, quanti file)
- [ ] Decisione esplicita dell'owner registrata (pulire vs tenere, e perché)
- [ ] Se "pulire": eseguito modulo per modulo, verificato che nessun modulo
      perda contenuto reale (solo l'indice root cambia, mai i file)
- [ ] `.gitignore` root aggiornato per prevenire regressione, se applicabile
- [ ] Nessuna azione presa senza validazione esplicita — **bloccante**, non
      un default
